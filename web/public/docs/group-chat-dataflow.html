Stella · Group chat · Development reference

Optimistic group collaboration

Every ordinary group message wakes eligible members; a nudge targets one agent. Each agent decides locally whether it has anything to say; one locked transaction accepts a pending reply, and publisher success finalizes its delivery and peer wake. No model decides whether another model may speak.

Figure 01 · Architecture

One pipeline, from ingest to egress

Web and platform messages share one path. Ingest appends a canonical event and fans out eligible dispatch rows; the per-agent worker serializes wake and nudge work; the accept transaction is the single place a reply can still be stopped.

Why the accept transaction exists

  • The only place that sees the group under a lock, after the agent finished thinking
  • Commits the pending reply, memory turn and cursor together
  • Publisher success finalizes delivery and creates the peer outbox
  • A stale reply stays held unless failed delivery compensates it

Why newest-wake-wins

  • A busy group coalesces stale snapshots instead of queueing a turn per message
  • Five messages in a row cost one turn that sees all five
  • Superseded wakes never advance the memory cursor

Web is a platform

  • POST /messages only ingests and wakes workers
  • Its publisher is a noop, not a bypass
  • pending → publisher finalizes delivered / failed

Figure 02 · Sequence

Two agents, one message

Both agents are woken by the same message and both think against the same snapshot. The accept transaction serializes them: the first commits a pending reply, the second is held against the stale snapshot, and a later, separate pending wake must cover that sequence.

Shown implies seen

  • A hold records held_up_to_seq
  • The claim gate refuses any wake older than it
  • So B's next snapshot always covers what caused the hold

Holds are bounded

  • hold_limit (default 3), counted within ctx_group_chain_root
  • Past it, a stale reply continues to dedup and cap checks
  • It is then normally accepted, so a slow agent is not starved forever

A rejected ending is not a forgotten turn

  • A post-turn hold commits the history and tool work actually read
  • Its cursor advances through the trigger sequence
  • Only the rejected trailing reply is discarded

Figure 03 · State machine

The life of a wake row

One durable dispatch row per eligible wake: normal fan-out skips the agent author and a nudge has one target. A database claim is running, but only a turn that passes triage emits a running frame, so a UI badge always resolves.

One running, one terminal

  • Every emitted running frame owes exactly one terminal frame
  • A gate decline is database-running but emits only silent
  • Superseded rows emit no turn frame; frames are live-only and never replayed

What advances the cursor

  • completed, silent(model_pass) and post-turn backstops do
  • They commit history and tool work through the trigger, not the rejected ending
  • superseded and pre-turn gate declines do not advance the cursor

Crash recovery

  • Ordinary work has 3 attempts, the initial try plus 2 retries
  • Ambiguous accepted delivery can recover up to 10 attempts
  • Only terminal accepted-delivery failure frees held peers
