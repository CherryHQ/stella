Group Chat 统一数据流

目标模型：Web UI 和平台适配器（Telegram / QQ / Feishu）共用同一条管线： triple resolve → dedup event log → durable outbox → dispatcher worker → dispatch ledger → publisher(reply_channel_id) → hybrid memory → LLM → writeback。 本文档追踪一条消息从入口到渲染的完整路径，并标出当前实现仍需补齐的 gap。

01 Triple Resolve + Dedup 写入 eventlog.go (target)
目标态下，所有入口都调用同一个 ingest 原语。适配器只负责收消息并写入事实：resolve group_id → dedup check → bump seq + insert message → insert dispatch outbox，全部在同一个 BEGIN IMMEDIATE 事务里完成。adapter 不再直接负责回复。
AppendGroupMessage 调用 Go

    Platform:          "telegram",
    PlatformGroupID:   "-10012345",
    PlatformThreadID:  "",               ← triple 的第三维
    SourceChannelID:   "tg-bot-weather",  ← 观察者 bot，仅审计；不参与 dispatch
    ActorType:         "human",
    ActorID:           "uid_88",
    PlatformMessageID: "tg_msg_9001",    ← Tier 1 dedup key
    PlatformTimestamp:  msg.Timestamp,    ← Tier 2 fallback key
    Content:           "@weather-bot 北京今天天气怎么样？",
})
内部三步 SQLite 
-- Step 0: resolve group_id (get or create)

WHERE platform='telegram' AND platform_group_id='-10012345'
  AND platform_thread_id='';
-- → grp_9f3a

-- Step 1: Tier 1 dedup — 按 platform_message_id

WHERE group_id='grp_9f3a' AND platform_message_id='tg_msg_9001';

  platform_message_id, content, ...)

  'tg_msg_9001', '@weather-bot 北京今天天气怎么样？', ...);

-- Step 3: same transaction outbox — “这条事实需要被调度”
INSERT INTO ctx_group_outbox (id, group_message_id, group_id, seq, status)
VALUES ('outbox-uuid-1', 'uuid-new', 'grp_9f3a', 42, 'pending');
Dedup 两层

Tier 1：platform_message_id — 平台提供的稳定 ID，多个 bot 观察到同一条消息会合并。
Tier 2：SHA256(group_id + actor_id + timestamp + content) — 仅当没有稳定消息 ID、且有平台提供的高精度发送时间时启用。
Web 要求：前端必须发送稳定 client_message_id，服务端把它作为 platform_message_id；不要用服务端接收时间做 dedup。
无 key：两者都没有时，永远插入（不做 dedup）。

Dispatch gate

只有首次插入的 human message 才创建 outbox。幂等重投返回 existing seq 后必须停在 ingest 层：不 bump seq、不创建 outbox、不重复 arbiter、不重复回复。调度是否完成由 outbox / dispatch ledger 记录，不靠接收 adapter 的调用栈。

seq 是 per-group monotonic，不是全局递增。 UNIQUE(group_id, seq)。不同群组的 seq 互相独立。

03 Arbiter 路由决策 + Dispatch Ledger arbiter.go + ctx_group_dispatch (target)
Arbiter 是统一的路由闸门。目标态下 Web 和 Platform 都不绕过它：@mention 直达，否则由 arbiter 选择响应者，并应用 reply cap / debounce。决策结果落到 dispatch ledger，记录 哪个 agent 该通过哪个 reply_channel_id 发言、是否已经完成。
Arbiter.Decide 调用 Arbiter 
policy := LoadGroupDispatchPolicy(groupID)  // target: per-group config

 decision := arbiter.Decide(ctx,
    groupID:        "grp_9f3a",
    mentions:       [{AgentID: "weather-bot"}],
    groupMembers:   ["weather-bot", "travel-bot"],
    channelAgentID: "weather-bot",  ← channel default (fallback)
    channel.DecideOptions{AllMembersFallback: policy.AllMembersFallback},
)
决策树 (三条路径)
有 @mention?
→ 直达被 mention 的 agent(s)
跳过 debounce。过滤只保留群组成员。受 MaxRepliesPerTrigger 上限。
本例命中此路径 → responding = ["weather-bot"]
无 mention + 有 channelAgent
→ 检查 debounce window。未被抑制则 channel default agent 响应。
DebounceWindow > 0 时，同一群组内 window 内的非 mention 消息被静默跳过。
无 mention + 无 channelAgent
→ AllMembersFallback=true：所有成员响应（受 MaxReplies 上限）。
→ AllMembersFallback=false：不响应（静默跳过）。
ArbiterConfig Config 
type ArbiterConfig struct {
    MaxRepliesPerTrigger int            // 0 → default 1; 每条消息最多触发几个 agent
    DebounceWindow       time.Duration  // 0 → 不 debounce; 同群组非 mention 消息最小间隔
}

// 目标默认: MaxReplies=1，避免无 @ 时炸群
// AllMembersFallback 存在 per-group dispatch policy；当前 Web 硬编码 true，迁移后变成显式配置
决策结果 Output 
ArbiterDecision {
    RespondingAgents: ["weather-bot"],  ← @mention 直达
    Debounced:        false,
}

04 Publisher by reply_channel_id publisher registry (target)
dispatcher claim pending dispatch row 后，只按 selected agent 的 reply_channel_id 查 publisher。publisher 是平台出口：它负责 resolve session → Chat → 用自己的平台 API 发消息 → writeback。观察到消息的 bot 不是回复身份。
Context + Dispatch Go 
// claim dispatch row，保证同一 agent 对同一 message 只执行一次
dispatch := ClaimGroupDispatch(ctx,
    groupMessageID: "uuid-new",
    agentID:        "weather-bot",
)

publisher := publisherRegistry.Get(dispatch.ReplyChannelID)
if publisher == nil {
    RetryOrFailDispatch(dispatch, "publisher unavailable")
    return
}

// 注入 triggerSeq — 所有 agent 共享同一个
ctx = memory.WithGroupSeq(ctx, dispatch.Seq)

publisher.PublishGroupResponse(ctx, GroupDispatchRequest{
    GroupID:        dispatch.GroupID,
    AgentID:        dispatch.AgentID,
    ReplyChannelID: dispatch.ReplyChannelID,
    TriggerSeq:     dispatch.Seq,
})

// publisher 内部：session resolve → Chat() → platform API → AppendToGroup writeback
// 成功：status=completed；失败：attempt_count++，按 backoff 设置 next_attempt_at；超过上限 status=failed
Retry / lease policy

Claim 使用 status='pending' AND (next_attempt_at IS NULL OR next_attempt_at <= now)，以及 status='running' AND lease_until < now 的过期租约回收。执行期初始 lease 建议 10 分钟，长工具调用可 heartbeat 延长。失败时递增 attempt_count 并指数退避；超过 MaxDispatchAttempts 后标记 failed，写 log/metric，平台侧不冒名 fallback。

06 同轮隔离机制
当 MaxReplies > 1 时多个 agent 在同一轮响应。它们共享同一个 triggerSeq， 所以 agent 之间看不到彼此本轮的回复。这是 by design 的隔离。
假设 travel-bot 也被选中 对比 
// travel-bot 的 assembleGroup:
watermark  = 39    ← 自己的 cursor
triggerSeq = 42    ← 共享同一个 baseCtx

// between-turn: seq > 39 AND seq < 42
// seq=40: weather-bot "周末天气晴朗…" → 注入
// seq=41: travel-bot  "推荐故宫…"     → self, 跳过

// ⚠️ weather-bot 本轮回复 (seq=43) 不在范围内
// 因为 43 > triggerSeq=42 → 被 beforeSeq 排除
// 这保证同轮 agent 之间不会互相影响
设计意图

同轮隔离避免了串行执行时后面的 agent 被前面 agent 的回复干扰。 所有 agent 看到的上下文是确定性的（由 triggerSeq 锚定）， 不依赖执行顺序。本轮 agent 回复会在 下一轮 通过 between-turn 注入。

Web vs Platform 差异点

统一管线下，两个入口的差异仅限于接入层和输出层，核心逻辑完全共享。

阶段 Web UI Platform Adapter
入口 POST /api/groups/:id/messages Telegram webhook / QQ gateway / …
Triple ("web", groupId, "") ("telegram", "-10012345", "42")
Dedup AppendGroupMessage — 共享 Tier 1/2 dedup
@Mention 解析 解析 @AgentName 文本匹配 平台 mention → botRegistry → agentID
Outbox 首次插入 human message 时同事务创建 pending outbox；duplicate 不创建
Arbiter + Ledger dispatcher worker claim outbox → Arbiter.Decide() → ctx_group_dispatch pending/running/completed
Memory assembly 共享 assembleGroup() — hybrid LCM + event log
Publisher web publisher：绑定当前 POST/SSE 连接；连接断开后仍以 event log writeback 为准 channel publisher：按 reply_channel_id 使用对应 bot/token 调平台 API
Writeback 共享 AppendToGroup — agent 回复写回 event log
渲染 useChat → GroupTranscript → per-agent bubbles 平台原生消息（单条文本/Markdown）
Cross-adapter 不适用（同一 Web 连接） dispatch 不绑定 observer adapter；publisher registry 按 selected agent 的 reply_channel_id 发布；fallback 到 channel default 被禁止

已知风险

CR-006 — 水位线提前推进

UpsertIngestCursor 在 assembleGroup() 内执行，早于 Chat() 调用。 若 LLM 调用失败，cursor 已推进，between-turn 消息永久跳过。 修复方向：拆分 assembly 为 prepare + commit，Chat 成功后再推进 cursor。

CR-009 — Dispatch 仍绑定 observer adapter

当前代码仍在接收消息的 adapter 调用栈内决定和执行回复；当 selected agent 的 replyChannelID 与观察者 bot 不同时，会静默跳过。目标模型把 ingest 和 dispatch 解耦：adapter 只写 event log/outbox；dispatcher worker claim outbox/dispatch ledger；publisher 按 reply_channel_id 发出。禁止 fallback 到 channel default 或 observer bot。

CR-012 — 无 channel default 且无 mention

如果群组没有设置 channel default agent，且消息不含 @mention， AllMembersFallback=false 时 arbiter 返回空 — 消息被静默忽略。 目标统一模型下，Web 也应走同一个 arbiter；全员响应只能是 per-group dispatch policy 里的显式配置，不是硬编码默认语义。
