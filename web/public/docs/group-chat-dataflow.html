Group Chat 统一数据流

目标模型：Web UI 和平台适配器（Telegram / QQ / Feishu）共用同一条管线： triple resolve → dedup event log → durable outbox → dispatcher worker → dispatch ledger → publisher(reply_channel_id) → hybrid memory → LLM → writeback。 本文档追踪一条消息从入口到渲染的完整路径。

01 Triple Resolve + Dedup 写入 eventlog.go (target)
目标态下，所有入口都调用同一个 ingest 原语。适配器只负责收消息并写入事实：resolve group_id → dedup check → bump seq + insert message → best-effort 解析 mention → insert dispatch outbox，全部在同一个 BEGIN IMMEDIATE 事务里完成。Web 同步路径在同一事务内直接以 running + lease 创建 outbox，避免后台 worker 抢单；adapter 不再直接负责回复。

Dedup 两层

Tier 1：platform_message_id — 平台提供的稳定 ID，多个 bot 观察到同一条消息会合并。
Tier 2：SHA256(group_id + actor_id + timestamp + content) — 仅当没有稳定消息 ID、且有平台提供的高精度发送时间时启用。
Web 要求：前端必须发送稳定 client_message_id，服务端把它作为 platform_message_id；不要用服务端接收时间做 dedup。
无 key：两者都没有时，永远插入（不做 dedup）。

Dispatch gate

只有首次插入的 human message 才创建 outbox。幂等重投返回 existing seq 后必须停在 ingest 层：不 bump seq、不创建 outbox、不重复 arbiter、不重复回复。平台入口创建 pending outbox 交给 worker；Web 同步入口创建 running+lease outbox 并立即执行，后台 worker 只在租约过期后用 NoopGroupPublisher 做 crash recovery。调度是否完成由 outbox / dispatch ledger 记录，不靠接收 adapter 的调用栈。

03 Arbiter 路由决策 + Dispatch Ledger arbiter.go + ctx_group_dispatch (target)
Arbiter 是统一的路由闸门。目标态下 Web 和 Platform 都不绕过它：@mention 走规则直达（L0）， 无 mention 时若配置了语义群仲裁（L1），则由 fast 模型判断该谁回复（定向 / 广播 / 静默），否则回退到旧的成员 fallback 规则。决策结果落到 dispatch ledger，记录哪个 agent 该通过哪个 reply_channel_id 发言、是否已经完成。

决策树 (三条路径)
有任意 @mention?
→ L0 规则路径
已解析到 Stella 群成员的 mention 直达对应 agent(s)，跳过 debounce，并绕过 MaxRepliesPerTrigger：一条消息 @ 多个成员时所有被 @ 的成员都会回复。 无法解析的 platform mention 不会被当成无 mention 语义请求；默认静默，避免回复本来发给别人的消息。
本例命中此路径 → responding = ["weather-bot"]
无 mention + 配置了语义仲裁 (L1)
→ semantic_group_arbiter.go：fast 模型读取有界历史群上下文（只取 seq < currentSeq）+ 有界公开成员描述，返回 {should_reply, agents[]}。定向 → 单个 agent；广播 → 多个（受自身 maxResponders 上限）；闲聊/超时/解析失败 → 静默。
路由模型按归属选取：Web 群优先群主自己的 agent，否则 system-scope；Platform 群仅 system-scope。所选 agent 用其 fast tier 分类，若未配置 model_fast 则自动回退到该 agent 的默认模型（不会因为没配快模型就静默）。私有 agent 的凭据不会被用于共享路由决策；成员摘要（system_prompt 前 180 字符）有意发给路由模型，用于正确路由。
分类调用有 8s 预算（覆盖首 token + 一小段 JSON）。失败均降级为静默，并按级别记日志：每条消息的 prompt / 原始响应 / 决策走 DEBUG，「本该路由却被吞」的降级（无可用模型、provider 报错、空响应、解析失败）走 WARN。
无 mention + 未配置语义仲裁（回退）
→ Web：单成员群直接让唯一成员回复；多成员群静默并写 WARN，提示配置语义仲裁。
→ Platform always：所有成员响应（受 MaxReplies 上限）。
→ Platform mention：不响应（静默跳过）。

04 Publisher by reply_channel_id publisher registry (target)
dispatcher claim pending dispatch row 后，只按 selected agent 的 reply_channel_id 查 publisher。publisher 是平台出口：它负责 resolve session → Chat → 用自己的平台 API 发消息 → writeback。观察到消息的 bot 不是回复身份。
Context + Dispatch Go

    groupMessageID: "uuid-new",
    agentID:        "weather-bot",
)

if publisher == nil {
    RetryOrFailDispatch(dispatch, "publisher unavailable")
    return
}

    GroupID:        dispatch.GroupID,
    AgentID:        dispatch.AgentID,
    ReplyChannelID: dispatch.ReplyChannelID,
    TriggerSeq:     groupMessage.Seq,
})

// publisher 内部：session resolve → Chat() → platform API → 同事务 AppendToGroup + result_message_id
// 成功：status=completed；失败：attempt_count++，按线性 backoff 设置 next_attempt_at；超过上限 status=failed
Retry / lease policy

Claim 使用 status='pending' AND (next_attempt_at IS NULL OR next_attempt_at <= now)，以及 status='running' AND lease_until < now 的过期租约回收。执行期初始 lease 默认 5 分钟，长工具调用可 heartbeat 延长。失败时递增 attempt_count 并线性退避（1s × attempts，封顶 60s）；超过 MaxDispatchAttempts 后标记 failed，写 log/metric，平台侧不冒名 fallback。 同一 agent 在同一 group 内按 seq 顺序领取：若存在更小 seq 的 pending 或未过期 running dispatch，后序行不会被查出，避免乱序执行。

At-least-once 收敛

发布语义是 at-least-once。正常收尾顺序是：Publish 成功 → 同一个 DB 事务内 AppendToGroup writeback + 写 result_message_id marker → 标记 completed。重试若看到 marker 已存在，会跳过 Chat 和 Publish，直接 completed。 因此 writeback 已提交后的崩溃不会重发；唯一残余重复窗口是平台 Publish 已成功、但 writeback+marker 事务尚未提交前进程崩溃。Web 的主交付通道是 event log，客户端断线后 服务端继续跑完；NoopGroupPublisher 用于重启后的恢复，不向客户端推 SSE。

// seq=41: travel-bot  "推荐故宫…"     → self, 跳过

// ⚠️ weather-bot 本轮回复 (seq=43) 不在范围内
// 因为 43 > triggerSeq=42 → 被 beforeSeq 排除
// 这保证同轮 agent 之间不会互相影响
设计意图

同轮隔离避免了串行执行时后面的 agent 被前面 agent 的回复干扰。 所有 agent 看到的上下文是确定性的（由 triggerSeq 锚定）， 不依赖执行顺序。本轮 agent 回复会在 下一轮 通过 between-turn 注入。

Web vs Platform 差异点

统一管线下，两个入口的差异仅限于接入层和输出层，核心逻辑完全共享。

阶段 Web UI Platform Adapter
入口 POST /api/groups/:id/messages Telegram webhook / QQ gateway / …
Triple ("web", groupId, "") ("telegram", "-10012345", "42")
Dedup AppendGroupMessage — 共享 Tier 1/2 dedup
@Mention 解析 解析 @AgentID 文本匹配 平台 mention → botRegistry → agentID
Outbox 首次插入 human message 时同事务创建 pending outbox；duplicate 不创建
Arbiter + Ledger dispatcher worker claim outbox → Arbiter.Decide() → ctx_group_dispatch pending/running/completed
Memory assembly 共享 assembleGroup() — hybrid LCM + event log
Publisher web publisher：绑定当前 POST/SSE 连接；连接断开后仍以 event log writeback 为准 channel publisher：按 reply_channel_id 使用对应 bot/token 调平台 API
Writeback 共享 AppendToGroup — agent 回复写回 event log

Cross-adapter 不适用（同一 Web 连接） dispatch 不绑定 observer adapter；publisher registry 按 selected agent 的 reply_channel_id 发布；fallback 到 channel default 被禁止
