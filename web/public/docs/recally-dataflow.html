Recally 订阅数据流

目标模型：Go 只拥有源无关的记账（feed / entry 表、guid 去重、调度、重试）； 抓取与总结下沉到 recally skill + tap。一个源加进来，只动 skill workflow（+ 也许一个 tap 脚本），不动 Go。核心翻转：正确性建立在 ON CONFLICT(feed_id, guid) 去重上，不靠 since 水位。 本文档追踪一条新条目从「发现」到「入库 + 通知」的完整路径。

kind = rss（公开 / 免登录）
recally tool：action=feed_poll
server 端 gofeed 解析，便宜稳定，零 LLM
→ 汇入 ←
kind ≠ rss（twitter / 未来源）
recally skill workflow
tap fxembed / browser 列出条目
源无关 dedup sink

recally tool：action=entry_add, feed_id, guid, url, title → POST /feeds/{id}/entries → CreateRSSFeedEntry （ON CONFLICT(feed_id, guid) DO NOTHING RETURNING *）：有行 = new，空 = dup

01 订阅 — URL 嗅探出 kind recally_handlers.go · types.go
feed add 从 URL 嗅探来源类型并落库。x.com / twitter.com 主机 → kind=twitter，其余默认 rss；--kind 是逃生舱。 非 rss kind 不走 server 端 gofeed 解析（那解析不了 x.com），title/description 留给 skill 回填。

kind := recally.SniffFeedKind(body.Url)  // x.com → twitter

if !kind.Valid() { /* 400 写入边界校验枚举 */ }

if kind == recally.FeedKindRSS {
    parsed, err := h.feeds.ParseURLWithContext(body.Url, ctx)  // 仅 rss 解析

}
// 非 rss：跳过解析，title 空着等 skill 回填
feed, _ := h.store.CreateFeed(ctx, userID, body.Url, kind, nil, title, description, agentID)

kind 是分流提示，不是业务分支

Go 存 kind 只为决定「调度走哪条路」，不在它上面分业务逻辑。 枚举（rss / twitter）在 Go 写入边界校验，schema 用 plain TEXT —— 新增 kind 不用迁移。 metadata 是 JSON blob，存数字 user-id 这种改名不变的标识。

02 调度 — recally-rss builtin 按 kind 分流 scheduler/builtin_rss.go
每 6h 起一个 agent session（ExecScopeAllUsers）。builtin 是一段 prompt，指示 agent 按 feed 的 kind 分发发现逻辑 —— rss 走 Go 快路径，非 rss 走 skill。
dispatch by feed.kind
kind == "rss" recally tool action=feed_poll 一次跑完所有 enabled feed。 server 端 gofeed 解析 + CreateFeedEntry 去重，非 rss feed 在 server 被短路成 no-op。
kind != "rss" feed list --json 取出 kind=twitter 的 feed，逐个跑该 kind 的 workflow （见 twitter-workflow.md）→ Stage 03。
PollFeed — 非 rss 短路 Go 
// 只有 rss feed 在 server 端轮询；skill 驱动的 kind 在这里是 no-op
if feed.Kind != recally.FeedKindRSS {
    writeData(w, http.StatusOK, result)  // 空 new_entries，无害
    return
}
03 发现 — skill 列推文（仅 twitter 路径） references/twitter-workflow.md
agent 用 tap 的 FxEmbed 脚本列出最近推文。since 只是省流量的优化， 坏了不影响正确性 —— 每轮把列出的推文全部推给 sink，去重交给 Go。
tap fxembed-profile-statuses tap 
# 用 metadata.external_id 的数字 id，防 handle 改名
tap site twitter/fxembed-profile-statuses handle=id:33836629 --json
每条 status 的处理 skill 
tw_1002  is_repost=false  → guid=tw_1002  url=…/status/1002  title="New post on …"  push
tw_1001  is_repost=false  → guid=tw_1001  (上轮已 saved)                          push
rt_99   is_repost=true   → skip retweet（默认跳过）
空正文  → title fallback "(media: Andrej Karpathy)"
为什么不在 skill 里判断「这条是不是新的」

判新是有状态的，扔给 LLM loop 就脆。skill 只做无状态的「列出 + 映射 + 推送」， 有状态的去重收口在 Go/SQLite 的一句 ON CONFLICT 里。

04 去重 sink — guid upsert，只有 new 变 pending queries/recally_feed.sql · store.go
两条发现路径汇到同一个端点。这是整条流的命门：去重发生在抓取/总结之前。 一条重复的推文在这里被 DO NOTHING 挡掉，根本不会产生新的 pending 条目。
CreateRSSFeedEntry — 仓库现成的去重 SQLite 
INSERT INTO recally_feed_entry (id, feed_id, guid, url, title, status, ...)
VALUES (?, 'feed_7c', ?, ?, ?, 'pending', ...)
ON CONFLICT(feed_id, guid) DO NOTHING
RETURNING *;   -- 有行 = new；DO NOTHING 命中冲突 → 无行 = dup
本轮两次 push 的结果 CLI 
feed entry add --guid tw_1002  → new   // 插入 status=pending
feed entry add --guid tw_1001  → dup   // 已存在，什么都不做
recally_feed_entry — sink 之后 SQLite
id feed_id guid status attempts article_id
en_a1 feed_7c tw_1001 saved 1 art_x
en_b2 feed_7c tw_1002 pending 0 —
会重复总结吗？不会。

总结发生在 Stage 05（save-workflow），而 save-workflow 只处理 pending 条目。 tw_1001 在 sink 返回 dup、未产生新 pending → 轮不到它被抓取和总结。 每轮重复的只是「列推文 + guid upsert」这种零成本操作，贵的 LLM 总结永远只对真正新增的条目跑一次。

correctness = guid dedup, not watermark

抓取失败那轮就是「没发现新条目」，下一轮重列、重推，重复的被 DO NOTHING 丢掉 → 永不丢条目，也不需要脆弱的「成功才推进 since」逻辑。这条把 reviewer 当初的 BLOCK 直接消解。

05 抓取 + 总结 — agent 自己干，无 Go 代码 references/save-workflow.md
对每个 pending 条目（含重试：status IN ('pending','error') AND attempts < 3）， agent 跑 save-workflow。这一步的「总结」不是 Go 里的代码，也不是单独的 LLM API 调用 —— 就是当前 agent（即 LLM 本身）读完正文后生成的一段文本。
5a · Fetch 全文到临时文件
tap 抓取（含升级链） tap 
tap site twitter/fxembed-status id=tw_1002 format=markdown -f raw > $f
# 通用页面升级链：tap fetch → --lp → Jina → -b → browser network intercept
5b · Generate Metadata — agent 读 $f，写结构化总结
$sf — agent 生成（非代码） LLM 
# Summary      (2-3 句) 摘要
# Abstract     (150-200 词)
# Key Points   要点 bullet
# Insights and Implications
# Actionable Takeaways (如适用)
# Critical Analysis
+ Title / Author / Tags(3-7) / Worth-Reading tier (⭐/👍/📖)
总结「跑」在哪

不在 stellad 进程里（Go 不调 LLM 做总结）；不是对 Anthropic/OpenAI 的独立请求。 就在当前这个 agent 会话的上下文里 —— 调度器起的 agent 一路抓取、总结、调 CLI 保存， 总结只是它的一段文本输出。skill 文件本质是 prompt，不是可执行代码。

06 入库 + 标记 — 文章持久化，条目转 saved recally save · feed mark
recally tool action=save 是纯持久化动作：给它 summary 字符串，它原样存进 recally_article，不关心这字符串怎么来的。保存后把 entry 标记为 saved。
save → update entry Tool 
recally action=save items=[{
  url: "https://x.com/karpathy/status/1002",
  content: "<fetched markdown>",
  summary: "<curated summary>",
  title: "…",
  author: "Andrej Karpathy",
  tags: ["ai", "ml"],
  source_type: twitter,
  metadata: {"worth_reading":"Top pick"}
}]

recally action=entry_update feed_id=feed_7c id=en_b2 status=saved article_id=<saved article id>
# 失败：status=error error_msg="<reason>"  ／ 跳过：status=skipped
recally_article — 落库一条 SQLite
id user_id source_type title status
art_y u_42 twitter New post on … unread
第二层保险 — 文章级去重

即便 dup 漏到这步，recally save 还按 canonical URL 做文章级去重 （mobile/desktop 变体可能各算一份）。但正常路径在 Stage 04 就拦住了，到不了这层。

07 通知 + 摘要 builtin_rss.go · recally digest
仅当本轮 ≥1 篇文章被保存时才调一次 notify（零保存就停手，不打扰）。每日 digest 另行汇总。
notify 门槛（builtin prompt） skill 
saved == 0  → 不调 notify，结束
saved >= 1  → notify 一次：
  · 每篇(最多5)：Worth-Reading 标签 + 标题 + 作者 + "# Summary" 段
  · 超过5篇：其余仅列 标题 + 作者

RSS vs Twitter 差异点

两条路只在「发现」环节不同 —— auth 边界才是真正的分界，不是源类型。一旦成了 pending 条目，抓取 / 总结 / 入库 / 通知走的是同一条路。

阶段 RSS (kind=rss) Twitter (kind=twitter)
订阅嗅探 默认 kind=rss x.com / twitter.com → kind=twitter
入库时解析 server gofeed 取 title/description 跳过解析，skill 回填 + 存数字 user-id
发现执行者 server（Go 快路径，零 LLM） agent skill + tap fxembed
列出条目 gofeed 解析 RSS items fxembed-profile-statuses，跳 retweet
去重 共享 feed entry add — ON CONFLICT(feed_id, guid) DO NOTHING
抓取 + 总结 共享 save-workflow — agent 读全文，LLM 生成结构化总结（仅对 pending 条目）
入库 共享 recally save → recally_article（canonical URL 二次去重）
source_type rss twitter
通知 / 摘要 共享 notify 门槛 + 每日 digest
成本优化空间 已是最便宜路径 per-source 缓存折叠重复抓取（v2 / #316）

auth 边界 — 框架的真正分界（#316）

决定一个源能不能留 Go 快路径的，不是「它是什么源」，而是「需不需要登录」。

公开 / 免登录

RSS、YouTube 频道 RSS、fxtwitter 公开主页 —— 可留 Go 快路径作成本优化， 避免每轮起一个 LLM。YouTube 频道今天就能用：直接订阅 youtube.com/feeds/videos.xml?channel_id=…，零新代码。

登录态

X following / for-you / bookmarks、付费内容 —— 只能走 tap 的 attached browser， 在 agent 会话内执行 → skill-only，没有 Go 路径可言。
