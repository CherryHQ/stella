Goal 生命周期 · 规划门数据流

目标模型（#525）：每个 goal 在执行前都必须穿过显式的规划门。计划永远是一个版本化 artifact（agent_goal_plan），不是特殊任务。轻量 goal 走退化的 direct 计划，复杂 goal 走 checklist / sdlc 计划；两条路径之后共用同一条链路： accepted plan → 物化 work tasks → worker 带 goal context 执行 → 结构化 handoff → rollup。没有 accepted 计划，任何 goal work 都不会开始。

完整状态机 — Plan / Goal / Task 三泳道
Plan agent_goal_plan.status
draft → SubmitForReview in_review → Accept / Approve accepted / approved → Materialize materialized_at ✓ · superseded
Goal agent_goal.status
draft → CreateGoalPlan planning → Materialize planned → ActivateGoal running → Rollup done / blocked failed cancelled
Task 每个物化子任务 · agent_task.status
draft → Activate(随 goal) ready → Claim running → Submit reviewing → decide done / blocked failed cancelled

planned = accepted 计划存在 且已物化。关键不变式：只有 MaterializeGoalPlan 能把 goal 置为 planned；Accept / Approve 一律把 goal 留在 planning。direct 路径在同一事务里 accept + 物化 + 激活，瞬间从 planned 直达 running（"direct" = 直接做，无需单独 activate）； reviewing 仅当 task review_policy ≠ none 时出现，否则 Submit 直接 running → done。

跨泳道耦合 — 三个状态机如何联动
触发 本泳道转换 对其他泳道的级联效果
CreateGoal(direct) Plan: ∅ → accepted → materialized 同事务把 Goal 一路推到 running（accept+物化+激活），并物化出 1 个 Task(ready)
MaterializeGoalPlan Plan: accepted → materialized_at ✓ Goal planning → planned；建出 N 个 Task(draft) + deps + criteria
ActivateGoal Goal: planned → running 所有子 Task draft → ready（promoteChildren）
Claim → Submit Task: ready → running → done 每次 Task 转终态后触发 RollupGoal 重新评估 Goal
Task → done（全部 required） Task: → done RollupGoal：Goal running → done
Task → blocked / failed Task: → blocked / failed RollupGoal：Goal → blocked（可恢复）/ → failed（required 失败级联）
CancelGoal Goal: → cancelled 级联取消所有非终态子 Task → cancelled
Task reviewing 复审分支 — decideTaskReviewInTx

仅当 task review_policy ∈ {auto, human, agent} 时，Submit 把 task 送进 reviewing（none 则直接 done）。复审决策决定它的去向：

reviewing → ?（review.go · ApproveReview / RejectReview / RequestChanges）
approved Task reviewing → done。触发 RollupGoal 重新评估 goal。
changes_requested 还有 retry budget → Task reviewing → ready（消耗一次重试，重新 Claim 执行）； budget 耗尽 → reviewing → failed。
rejected Task reviewing → failed。required task 失败 → RollupGoal 把 goal → failed。
escalated 仅 reviewer_type=agent 可升级：原 review 关为 escalated，新建一个 human agent_review（escalated_from_review_id 回指），Task 停留 reviewing，active_review_id 指向新 review。

Plan 复审 ≠ Task 复审。 上表是 task 完成复审。计划的 human review 走专用的 ApproveGoalPlanReview / RejectGoalPlanReview / RequestChangesGoalPlanReview，绝不复用 goal 级 ApproveReview（那会把 goal 直接标 done）。计划批准只改 Plan 泳道，goal 仍留在 planning，直到物化。

01 Intent — 创建 goal 并选 PlanMode service_facade.go · CreateGoal
用户或 agent 通过 CreateGoal 建目标。CreateGoalInput 新增 PlanMode 字段（默认 direct）决定这个 goal 走哪条规划路径。 轻量需求用 direct 保持原有体验；复杂需求用 deferred，避免被塞进一次性的 direct 计划。
CreateGoalInput Go 
goal, err := facade.CreateGoal(ctx, tasks.CreateGoalInput{
    UserID:   "uid_88",
    AgentID:  "agent_eng",
    Title:    "把登录接口迁移到新鉴权",
    PlanMode: tasks.PlanModeDeferred, ← direct(默认) | deferred
})
// direct  → 自动 建+accept+物化+激活 direct 计划 → goal=running
// deferred → goal=draft，等待显式 CreateGoalPlan
PlanMode 分支
direct（默认） 同事务：一条 item 的计划 → accept → 物化一个 task → 激活 → goal running，child task ready 立即开始。"direct" = 直接做，无需单独 activate。
deferred goal 停在 draft，不自动建计划；调用方随后驱动 checklist / sdlc 的 CreateGoalPlan。
02 Plan — 版本化计划 artifact plan_service.go · agent_goal_plan
计划是独立的版本化 artifact，不是特殊 agent_task。direct 计划也是一个有效计划，不是 “没有计划”。这让下游（物化、context packet、handoff）始终走同一条路径。

03 Materialize — 计划落成 work tasks plan_service.go · MaterializeGoalPlan
服务端把 accepted / approved 计划幂等地转成子 agent_task + 依赖 + 验收标准。 planner 永远不直接建 work task —— 物化是唯一入口。成功后置 materialized_at，goal → planned。

硬 gate — 禁止手写 goal 子任务

public CreateTask 带 goal_id 一律拒绝 （ErrPlanMaterializationRequired），facade 和 HTTP handler 都返回 4xx。所有 goal work task 只能来自物化。提示词不是安全边界 —— 这条服务端约束才是。物化后再接受新计划版本会撞 uniq_current_accepted_goal_plan：MVP 直接返回 ErrPlanAlreadyMaterialized（re-plan 留给未来 slice）。

04 Activate — 规划门 goal_transitions.go · ActivateGoal
激活是 goal 进入执行的唯一闸门。它把所有不变式收口在一个转换里，子任务随之 draft → ready。
ActivateGoal 守卫 Go 
func (s *TransitionService) ActivateGoal(ctx, goalID) error {
    g := load(goalID)
    if g.Status != "planned"            { return ErrAcceptedPlanRequired }
    plan := getAcceptedPlan(goalID)
    if plan == nil                      { return ErrAcceptedPlanRequired }
    if !plan.MaterializedAt.Valid       { return ErrPlanNotMaterialized }
    if requiredChildren(goalID) == 0    { return ErrPlanNotMaterialized }

    setGoalStatus(goalID, "running")      planned → running
    promoteChildren(goalID)               draft → ready
}
为什么物化必须先于激活

若把物化推迟，direct goal 会被激活成没有子任务的 running： RollupGoal 对 0 个 required children 是 no-op，goal 永远卡在 running，而且会错过 draft → ready 的提升。所以 direct 路径在创建时就物化，materialized_at 是激活的硬前提。

05 Execute — dispatcher 认领 + context packet dispatcher.go · executor.go · goal_context.go
dispatcher 扫描 ready 任务、解析 executor、Claim 出一个 worker run。worker 执行前， GoalContextPacketBuilder 把紧凑的 goal / 计划切片注入 prompt —— 不塞全量计划， 不塞所有上游输出。
GoalContextPacketBuilder.Build(taskID) Go 
type GoalContextPacket struct {
    Goal         GoalSlice        title / objective
    Plan         PlanRef          id / version / type / status
    Item         ItemSlice        plan_item_id / sdlc_phase / 验收标准
    Upstream     []HandoffSummary 仅直接 hard 依赖、已 done 的 handoff 摘要
    Retrieval    Handles          按需拉全量计划 / 上游详情的句柄
    StaleWarning string           本任务 plan_version < 当前 accepted 版本时告警
}
紧凑而非倾倒

默认只注入当前任务切片 + 直接上游 handoff 摘要 + 检索句柄。完整计划、全部任务输出、传递性祖先都不默认进 prompt —— 需要时按句柄拉取。soft 依赖缺失永不阻塞。

06 Handoff — 结构化交接，单点强制 review.go · Submit · worker.go
plan-backed 任务的 task_control submit 输出必须带结构化 handoff。在 TransitionService.Submit 单点校验（所有 worker / API submit 都汇入这里），不另建 handoff 表 —— agent_task.output 就是事实源。
submit output handoff 形状 JSON 
{
  "result": { },
  "handoff": {
    "summary": "改了什么、下游需要知道什么",  ← 唯一硬性必填
    "artifacts": [], "decisions": [], "changed_files": [],
    "validation": [], "open_questions": [],
    "next_recommendations": []   ← 仅建议；不能借此绕过计划创建新任务
  }
}
失败路由 — 进 retry budget Go 
err := svc.Submit(ctx, taskID, runID, output, actor)
if errors.Is(err, ErrInvalidHandoff) {
    // 不是静默 return；收口成可重试失败 + protocol_error 事件
    return svc.Fail(ctx, taskID, FailInput{Retryable: true,
        Reason: "missing structured handoff"})
}
// retry budget(max_retries) 终止循环：耗尽后 task → failed，不会空转
standalone 任务保持灵活

handoff 强制只作用于 plan-backed 任务（source_plan_id 非空）。非 goal 的独立任务 output 仍然自由，向后兼容。

07 Rollup — goal 收敛终态 goal_rollup.go · RollupGoal
每次子任务转终态后，RollupGoal 用决策表判断 goal 走向。pre-run 状态 （draft / planning / planned）被 rollup 跳过。
RollupGoal 决策表（running 之后）
全部 required done goal → done（review_policy=none 时直接完成）
required child blocked goal → blocked，blocker 解除后回 running
required child failed goal → failed（依赖失败级联）
用户取消 goal → cancelled，级联取消非终态子任务
完整执行链回顾

user intent → accepted plan → materialized work tasks → worker（带 goal context）→ 每个任务的结构化 handoff → goal rollup。每一环都假设“计划永远存在”，所以 direct 与 sdlc 共用同一套物化 / context / handoff 代码，无需为轻量 goal 开特例。
