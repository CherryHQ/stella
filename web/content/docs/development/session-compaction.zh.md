---
title: 会话压缩
---

> 本节面向为 Stella 贡献代码的开发者。

## 状态

已实现 -- `internal/agent/pool_compaction.go`（编排）、`memory.Engine`（SQLite 持久化）、通道暴露 `/compact`。

## 问题

LLM runner 具有有限的上下文窗口。随着会话累积消息，历史记录无限增长。最终 runner 的上下文填满，导致响应降级或硬故障。长期会话（Telegram 聊天、多日编码会话）很快就会遇到这个瓶颈。

我们需要一种在不丢失关键上下文的情况下压缩旧历史记录的方法，并且不需要用户手动启动新会话。

## 设计：移交式压缩

核心思想借鉴了编码代理使用的"移交"模式：当上下文变得太大时，要求 LLM 本身生成一个自包含的摘要，然后用该摘要加上少量最近消息的尾部替换旧历史记录。

```
压缩前：
┌──────────────────────────────────┐
│ 会话头                           │
│ 消息 1                           │
│ 消息 2                           │
│ ...                              │
│ 消息 N-20                        │
│ 消息 N-19                        │  ← 逐字保留
│ ...                              │
│ 消息 N                           │
└──────────────────────────────────┘

压缩后：
┌──────────────────────────────────┐
│ 会话头                           │
│ 压缩 { 摘要 }                    │  ← LLM 生成的摘要
│ 消息 N-19                        │  ← 保留最后 20 条消息
│ ...                              │
│ 消息 N                           │
└──────────────────────────────────┘
```

摘要是结构化的，以便 runner 可以在没有原始消息的情况下继续对话 -- 它包含目标、进度、决策、更改的文件、当前状态、阻塞因素和下一步。

## 架构

```
Channel（/compact 或自动）
    |
    v
Pool.CompactSession(ctx, sessionID)
    |
    ├─ getOrCreateRunner()       如果需要从 SQLite 加载会话，确保 runner
    │
    ├─ collectFullResponse()     向 runner 发送压缩提示，收集摘要
    │
    ├─ memory.Engine compaction  在 SQLite 中存储摘要 + 尾部
    │
    └─ kill runner               下一个 Chat() 以干净的上下文重新开始
```

### Token 估计

Token 估计对存储消息的字节长度求和并除以 4（粗略启发式：英文文本加 JSON 开销每 token 约 4 字节）。

### 压缩提示

提示要求 runner 生成结构化摘要：

- **目标** -- 原始会话目标
- **进度** -- 已完成或部分完成的内容
- **关键决策** -- 决策和理由
- **更改的文件** -- 带上下文的路径
- **当前状态** -- 什么有效，什么无效
- **阻塞因素/陷阱** -- 问题或边缘情况
- **下一步** -- 具体、可操作的任务

指南强制自包含：摘要对于零访问先前对话的读者必须有意义。

### 存储格式

压缩摘要通过 `memory.Engine` 作为消息存储在 SQLite 数据库中。在 `Load()` 时，引擎将压缩条目转换为一对 `ai.Message` -- 包含摘要的用户消息和助手确认 -- 因此 runner 将其视为正常对话历史记录。

## 触发器

### 手动 -- `/compact` 命令

在 CLI 和 Telegram 中都可用：

```
/compact
```

直接调用 `Pool.CompactSession()`。向用户返回摘要文本。

### 自动 -- token 阈值

`Pool.Chat()` 在每条消息之前检查 `Pool.NeedsCompaction()`。如果估计的 token 计数超过阈值，则在发送用户消息之前自动运行压缩。

如果自动压缩失败，系统会记录警告并继续使用完整历史记录 -- 它永远不会阻止用户的消息。

## 配置

压缩设置作为 JSON 存储在数据库设置表中的 `compaction` 键下。它们可以通过管理面板或设置 API 配置。

字段：

- `max_tokens`：自动压缩阈值（默认：80,000；设置为 `-1` 禁用）
- `keep_tail`：逐字保留的最近消息（默认：20）

两个字段都通过 `CompactionConfig.WithDefaults()` 应用默认值。

将 `max_tokens` 设置为 `-1` 会禁用自动压缩；`/compact` 仍可手动工作。

## 有状态 Runner

一些 runner（如 Pi 子进程）在进程中维护自己的上下文，并忽略传递给 `Chat()` 的 `history` 参数。对于这些 runner，压缩后杀死进程将破坏实时上下文而没有任何好处 -- 新进程无论如何都无法重放压缩的历史记录。

Runner 通过实现可选的 `runner.Stateful` 接口来发出信号：

```go
type Stateful interface {
    Stateful() bool
}
```

当 runner 有状态时，`CompactSession()` 跳过 runner 杀死。压缩的历史记录仍然写入磁盘（用于崩溃恢复和会话恢复），但实时 runner 保持其进程内上下文完整。

对于从历史记录重建上下文的无状态 runner，runner 像以前一样被杀死，因此下一个 `Chat()` 调用以压缩的历史记录重新开始。

## 会话加载

`CompactSession()` 使用 `getOrCreateRunner()` -- 与 `Chat()` 相同的路径 -- 因此即使会话仅存在于磁盘上（例如，进程重启后或对于此进程生命周期中未访问的 Telegram 会话），它也能工作。这确保 `/compact` 始终可用于任何持久化的会话。

## 失败模式

| 场景              | 行为                               |
| ----------------- | ---------------------------------- |
| Runner 无法摘要   | 返回错误，会话未触及               |
| 数据库写入失败    | 返回错误，原始数据保留             |
| 自动压缩失败      | 记录警告，继续使用完整历史记录     |
| Runner 返回空摘要 | 返回错误："empty summary response" |

所有写入都通过 SQLite 事务以保证原子性。
