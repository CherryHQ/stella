## 1. 结论摘要

本轮评测支持以下结论：

1. **技术链路已经完整跑通。** Group Reflect 能从公开群消息生成候选，经独立评分和
   Host Gate 后，与现有 Group Facts 做 reconciliation，并通过真实 PostgreSQL、
   scheduler、生产 provider adapter 和 Agent runtime 完成写入与读取闭环。
2. **当前测试集下，Group Reflect 质量达到 V1 本地基线。**
   - 76/76 条 generation -> evaluation -> gate 用例通过；
   - 18/18 条固定候选的最终接受/拒绝决策正确；
   - 40/40 条单候选 reconciliation 通过；
   - 8/8 条多候选 reconciliation 通过；
   - 真实长会话 E2E 成功跨两个窗口处理，并在后续 Agent 回答中使用最新 Group Facts。
3. **该结论不是生产级质量证明。** 数据集是围绕当前需求人工设计的本地回归集，
   模型输出仍存在小概率波动，真实 E2E 只完成了一轮完整运行，也尚未进行生产流量、
   成本和大规模群数量压力测试。
4. **显式带截止时间的职责继续按短期信息处理。** 当前 Group Facts 没有结构化
   `expires_at` 和自动到期机制，因此“负责到本周五”“未来六个月负责”等内容均不进入
   Group Facts，由 per-Agent LCM 承载，避免到期后仍作为 active 长期事实注入。

## 2. 评测目标

本轮不把 Prompt 文案、候选数量、精确分数或 operation 排列当作最终产品目标。
验收关注以下实际行为：

1. 群协作所需的高密度、长期事实能够留下。
2. 工单状态、短期安排、显式到期职责、个人偏好、闲聊和敏感内容不会进入长期记忆。
3. Fact 能归属到正确的 `group`、`human` 或 `agent` subject。
4. 只有当前群内可解析的参与者才能成为 `human` 或 `agent` subject。
5. prior context 只能帮助理解，不能单独作为 fresh evidence。
6. 等价内容不重复写入；明确替换、交接和失效后，最终 active 状态正确。
7. 长会话分窗处理不丢失早期有效信号，也不反复处理已完成窗口。
8. 后续 Agent turn 能读取并使用最新 Group Facts。

以下内容只作为诊断信号，不单独决定产品是否合格：

- evaluator 的某个精确分数；
- generator 是否刚好输出某个固定候选数；
- reconciliation operation 的顺序；
- 单个窗口具体增加几个 group version；
- 当前权重、阈值、token budget 和候选上限。

## 3. 方法与环境

### 3.1 模型评测

四组本地 JSONL 数据集分别测试：

1. `candidate_eval.jsonl`
   - 使用生产 generation Prompt 和 tool schema；
   - 使用独立 evaluator 评分；
   - 使用生产 Host Gate；
   - 同时验收候选内容、subject、数量边界和最终接受结果。
2. `evaluator_eval.jsonl`
   - 输入固定 candidate；
   - 单独测试五维评分和 Host Gate；
   - 避免 generator 召回波动掩盖 evaluator 问题。
3. `reconciliation_eval.jsonl`
   - 输入已接受 candidate 和 active Group Facts；
   - 测试 `noop`、`create`、`replace_many`、`deprecate_many`。
4. `reconciliation_batch_eval.jsonl`
   - 同一窗口输入多个 candidates；
   - 测试跨主体 handoff、重复候选合并和组合操作。

所有模型调用均使用生产代码中的：

- Prompt；
- capture protocol；
- tool schema；
- schema validator；
- Host Gate；
- related bundle；
- reconciliation plan validator。

凭证只通过环境变量传入，未写入数据集、报告或代码。

### 3.2 真实链路 E2E

E2E 使用：

- 临时真实 PostgreSQL；

## 5. 分阶段结果

### 5.1 Generation -> Evaluation -> Gate

正式参考运行：

`dist/group-reflect-evals/757/20260725T051619Z/candidate.json`

结果：

- 76/76 case 通过；
- 0 provider/runtime error；
- 39 条 positive case 生成 49 个候选，49 个均通过 gate；
- 37 条 negative case 生成 0 个候选；
- 三种群聊拓扑全部覆盖并通过；
- `group`、`human`、`agent` 三类 subject 全部覆盖。

本组验证的关键边界：

- 用户可以陈述当前群内其他参与者的信息，不要求必须本人陈述；
- Agent 消息不能单独建立长期事实，只有被用户采纳、纠正、引用或依赖时才可作为补充；
- 无法解析为当前群 participant 的名字不能生成 participant Fact；
- prior-only 内容不能生成候选；
- 当前 ticket、临时任务、会议时间、显式到期职责和个人偏好不进入 Group Facts；
- 一次性权限不能被泛化为长期权限；
- 单次隐私请求不能被泛化为群级长期政策；
- 明确跨主体 handoff 会拆成新主体正向候选与旧主体失效候选。

### 5.2 独立 Evaluator 与 Host Gate

全量运行：

`dist/group-reflect-evals/757/20260725T052359Z/evaluation.json`

定向复跑：

`dist/group-reflect-evals/757/20260725T052504Z/evaluation.json`

结果需要分两层理解：

1. **接受/拒绝决策：18/18 正确。**
   - 7 条应接受 candidate 全部被 gate 接受；
   - 11 条应拒绝 candidate 全部被 gate 拒绝。
2. **精确评分断言：全量单次运行 17/18。**
   - `eval-negative-06-speculative-role` 的 `evidence_strength=0`，因此被 Host Gate
     正确拒绝；
   - 但模型按 candidate 字面中的 “standing responsibility” 给
     `durability=4`，超过测试要求的 `<=2`；
   - 定向复跑时该 case 给出 `durability=0` 并通过。

这说明 Host Gate 的最终安全边界稳定，但单个非决定性维度的精确分数会随模型运行
波动。报告因此不把“定向复跑通过”表述成“一次全量 18/18 精确评分通过”。

### 5.3 单候选 Reconciliation

正式参考运行：

`dist/group-reflect-evals/757/20260725T052806Z/reconciliation.json`

结果：

- 40/40 case 通过；
- 0 provider/runtime error；
- 四类 operation 全覆盖；
- 等价内容保持 noop；
- 明确新事实走 create；
- 同一 candidate 可以替换多条旧 facts；
- 纯失效信号只 deprecate 旧 Fact，不保存“某人已经不再负责”这类长期负面 Fact；
- 新消息与旧事实冲突但没有明确覆盖倾向时保持 noop；
- 明确替换倾向出现时执行 replacement。

### 5.4 多候选 Reconciliation

正式参考运行：

`dist/group-reflect-evals/757/20260725T052934Z/reconciliation_batch.json`

结果：

- 8/8 case 通过；

- 每个 candidate 在 plan 中恰好被覆盖一次；
- 同一 Fact 不会被多个 operation 重复修改；
- handoff 能形成“新主体 create + 旧主体 deprecate”；
- 等价候选能够合并；
- 不同 subject 的候选能够独立处理；
- noop 与有效写入可以在同一 plan 中共存。

## 6. 真实链路 E2E

本地 E2E 连续执行：

```text
创建长期群规则
-> 等价确认 no-op
-> 明确替换
-> 创建 participant 长期职责
-> 跨主体 handoff
-> 1,702 条长会话消息跨窗口处理
-> Runtime 注入最新 Group Facts
-> Agent 回答
```

结果：

1. 两人确认的“两审批”长期规则创建成功。
2. 等价确认没有创建重复 Fact，也没有推进 version。
3. “三审批”明确替换旧规则，旧 Fact 不再 active。
4. Alice 的长期 customer escalation 职责创建成功。
5. handoff 后 Bob 的职责 active，Alice 的旧职责 deprecated。
6. 长会话包含 1,700 条自然工单状态消息和 2 条长期规则消息：
   - 窗口一读取 1,600 条 fresh message，约 63,974 token；
   - 窗口二读取 102 条 fresh message，约 4,080 token，并附带约 16,000 token prior；
   - 只创建 1 条 incident handoff 长期事实；
   - 后续纯状态窗口创建 0 个候选；
   - Group Reflect watermark 最终推进到最后一条消息。
7. 最终只有 3 条 active Group Facts：
   - 三人审批规则；
   - Bob 的 customer escalation 职责；
   - incident commander written handoff 规则。
8. Agent provider Prompt 收到全部 3 条最新 Group Facts，最终回答正确使用了三审批、
   Bob 和 written handoff 信息。

E2E 首次扩展时曾因测试错误假设“每个窗口 version 只能增加 1”而失败。实际 handoff
包含 `create Bob + deprecate Alice` 两个有效写入，version 增加 2 是正确行为。测试随后
改为验收最终 active 状态、no-op 不推进和真实变更会推进，不再锁死内部 version 增量。

## 7. 评测中发现并修正的问题

本轮根据测试调整的是通用产品边界，而不是为单个 case 增加关键词：

1. 明确 fresh evidence 与 prior context 的职责，禁止 prior-only 候选。
2. 收紧个人偏好、当前 ticket、会议安排和显式到期职责。
3. 禁止从一次性操作推断长期权限或 standing authority。
4. 禁止把单次隐私请求泛化成长期群政策。
5. 加强 standalone invalidation 和 cross-subject handoff 的候选生成。
6. 要求 participant Fact 必须有可解析的 typed subject。
7. 明确新消息优先，但不把任意较新陈述自动当作长期覆盖。
8. 禁止 reconciliation 将“已不再负责”保存为新的长期负面 Fact。
9. 明确等价 candidate 应 noop，明确替换才 replacement。
10. 多候选 plan 中按 candidate 覆盖完整性和目标互斥做 Host 校验。

## 8. 已知波动与风险

### 8.1 模型非确定性

- 独立 evaluator 的一个 case 在全量运行中最终 gate 决策正确，但 durability 精确分数
  与预期不同；定向复跑恢复。
- 后续一次包含实验性额外 case 的 77-case candidate 运行中，原有 standalone
  invalidation case 曾出现一次不产候选；连续三次定向复跑均通过。实验性额外 case
  已撤回，不计入正式 76-case 结果，但该现象说明召回不是数学确定的。

因此当前结论是“在现有回归集上基本可靠”，不是“每次模型调用都必然得到同一结果”。

### 8.2 数据集偏差

- 数据集由当前方案的设计者编写，可能与 Prompt 边界存在共同偏差。
- 当前没有独立团队提供的盲测集。
- 当前没有使用不同模型作为 judge；主要依靠明确的 deterministic assertions 和人工
  检查代表性输出。

### 8.3 生产与规模

尚未验证：

- 大量群同时积压时的 30 分钟 run soft budget 行为；
- 单个 window 8 分钟 timeout 在真实 provider 波动下的失败率；
- 生产群数量下的数据库扫描耗时；
- 长期 token 成本和模型调用成本；
- 多次连续 E2E 的统计稳定性；
- 真实用户表达比当前数据集更含糊时的 precision/recall。

### 8.4 产品边界

- Group Facts 没有 usage 淘汰。
- Group Facts 没有内容级自动过期。
- 所有显式带截止时间的职责均拒绝进入 Group Facts，由 LCM 负责。
- 普通用户和会话工具不能直接查看或维护 Group Facts。

## 9. CI 与本地评测的边界

评测完成时，包含整条链路的本地实现已通过仓库的 format、build 和 test gate。拆分后，
各依赖切片分别运行同一套仓库 gate；最终集成切片还会再次验证组合后的完整代码。

CI 验证的是已推送产品代码。本文只提交结果摘要；本地模型评测框架、JSONL 数据集和
原始运行产物不上传，也不由 PR CI 执行。

此外，最后一次“显式带截止时间职责”规则回退后，按要求没有重复跑完整模型评测。
该回退恢复的是正式参考运行 `20260725T051619Z` 已验证过的旧边界，而不是引入新的
未测试行为。

## 10. 最终判断

当前 Group Reflect 可以进入代码评审和后续质量扩充阶段：

- 核心数据链路完整；
- 三类群聊拓扑和三类 subject 已覆盖；
- 当前本地回归集上的 precision、subject 路由、reconciliation 和长会话行为达到
  V1 预期；
- Runtime 已证明可以读取并使用写入后的 Group Facts。

但在正式把它描述为“生产质量已经达标”前，仍建议补充：

1. 一份与当前 Prompt 设计者独立的盲测集；
2. 多次重复完整 E2E，统计候选召回和错误写入波动；
3. 生产规模下的耗时、成本和 backlog 观测。
