## ロスレスコンテキスト管理（LCM）

### 概要

メモリシステムは、annaにロスレスコンテキスト管理を提供します。すべてのメッセージはSQLiteデータベースに永続化され、要約のDAG（有向非巡回グラフ）に編成されます。会話が長くなりすぎると、古いメッセージはリーフ要約にコンパクトされ、リーフ要約のグループはさらに高レベルの要約に凝縮されます。エージェントは任意の要約にドリルバックして元の詳細を復元できます -- 何も削除されません。

パッケージ：`internal/memory/`（コア）+ `internal/memory/tool/`（エージェントツールラッパー）。

### アーキテクチャ

```
ai.Message (user/assistant/tool_result)
        |
        v
  +----------+     ingest      +-----------+
  |  Engine   | -------------> | SQLite DB |
  +----------+                 +-----+-----+
     |    |                          |
     |    | compact                  |  Tables:
     |    v                          |    ctx_conversations
     | +------------------+          |    ctx_messages
     | | CompactionEngine | <--------+    ctx_summaries
     | +------------------+          |    ctx_items
     |                               |    ctx_summary_messages
     |  assemble (budget)            |    ctx_summary_parents
     v                               |
  +------------+                     |
  | Assembler  | <-------------------+
  +------------+
        |
        v
  []ai.Message (fresh tail + summaries within token budget)
        |
        v
  LLM context window
```

### Engine API

`Engine`インターフェース（`internal/memory/types.go`）がメインエントリーポイントです：

| メソッド                                      | 説明                                                       |
| --------------------------------------------- | ---------------------------------------------------------- |
| `Bootstrap(ctx, sessionID)`                   | セッションの会話レコードが存在することを確認               |
| `Ingest(ctx, sessionID, msg)`                 | 単一の`ai.Message`を永続化し、コンテキストアイテムを追加   |
| `IngestBatch(ctx, sessionID, msgs)`           | 複数のメッセージを単一のトランザクションで永続化           |
| `Assemble(ctx, sessionID, budget, freshTail)` | トークン予算内でコンテキストを構築し、`[]ai.Message`を返す |
| `Compact(ctx, sessionID, mode)`               | コンパクションパス（リーフ + 凝縮）を実行                  |
| `NeedsCompaction(ctx, sessionID, threshold)`  | コンテキストトークンが絶対閾値を超えているかチェック       |
| `Retrieval()`                                 | 検索/探索ツール用の`RetrievalEngine`を返す                 |
| `Close()`                                     | データベースリソースを解放                                 |

**コンストラクタ：** `NewEngineFromDB(db *sql.DB, summarizer Summarizer, opts ...EngineOption)`は既存の`*sql.DB`接続を受け入れるため、メモリエンジンは設定ストアや他のサブシステムが使用する同じデータベースハンドルを共有できます。

エンジンオプション：`WithFreshTail(n)`、`WithLogger(log)`。

### データベース

- **場所：** `~/.anna/anna.db`
- **ドライバー：** `modernc.org/sqlite`（純粋なGo、CGOなし）
- **モード：** WAL（書き込み中の並行読み取り）、外部キー有効
- **マイグレーション：** `internal/db/migrations/`のAtlas生成SQLファイル、`MigrationsFS`経由で埋め込まれ、`db.OpenDB()`で適用されます。適用されたバージョンは`schema_migrations`テーブルで追跡されます。

**スキーマ変更ワークフロー：**

```bash
# 1. スキーマソースファイルを編集
vim internal/db/schemas/tables/conversations.sql

# 2. マイグレーションを生成
mise run atlas:diff -- add_column_name

# 3. sqlcを再生成
mise run generate

# 4. ランタイムがOpenDB()で保留中のマイグレーションを自動適用
```

**スキーマ：**

| テーブル                  | 目的                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `ctx_conversations`       | セッションごとに1つ（`session_id` -> `id`マッピング）。会話を所有するエージェントとユーザーを追跡する`agent_id`と`user_id`列を含む。 |
| `ctx_messages`            | `role`、`content`、`token_count`、連続した`seq`を持つ生メッセージ                                                                    |
| `ctx_summaries`           | 要約ノード：`kind`（`leaf`/`condensed`）、`depth`、`content`、トークン統計、時間範囲                                                 |
| `ctx_items`               | 順序付けされたコンテキストウィンドウ：各アイテムは`message_id`または`summary_id`を指す                                               |
| `ctx_summary_messages`    | リーフ要約をそのソースメッセージにリンク（系統を保持）                                                                               |
| `ctx_summary_parents`     | 凝縮要約をその親要約にリンク（DAGエッジ）                                                                                            |
| `ctx_message_parts`       | 将来の使用のための構造化メッセージパーツ（`text`、`reasoning`、`tool`）                                                              |
| `ctx_agent_memory`        | ユーザーごと・エージェントごとのノート。主キーは`(user_id, agent_id)`。内容はセッション開始時にシステムプロンプトに注入される。      |
| `settings_agents`         | `system_prompt`（エージェントソウル）、モデル選択、ワークスペースパスを含むエージェント設定                                          |
| `settings_providers`      | LLMプロバイダー認証情報とエンドポイント                                                                                              |
| `settings_channels`       | チャネル（Telegram、QQ、Feishu）設定                                                                                                 |
| `settings_users`          | `ctx_agent_memory`と`ctx_conversations`によって参照されるユーザーレコード                                                            |
| `settings_channel_agents` | マルチエージェントルーティングのためのチャネルからエージェントへのマッピング                                                         |

### コンパクション

コンパクションは、古いメッセージと要約を要約することでコンテキストウィンドウを削減します。

**モード：**

| モード                  | 動作                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------------- |
| `CompactionIncremental` | 単一のリーフパス + 1つの凝縮パス。コンテキストが閾値を超えたときに自動実行されます。  |
| `CompactionFull`        | これ以上コンパクションができなくなるまでリーフ + 凝縮パスを繰り返します（最大10回）。 |

**パス：**

1. **リーフパス** -- フレッシュテール外のメッセージコンテキストアイテムの連続した実行を見つけます。≥ `DefaultLeafChunkSize`（10）のメッセージのグループは、`leaf`要約（深さ0）に要約されます。メッセージコンテキストアイテムは単一の要約コンテキストアイテムに置き換えられます。

2. **凝縮パス** -- 同じ深さの要約コンテキストアイテムの連続した実行を見つけます。≥ 2の要約のグループは、深さ+1の`condensed`要約に凝縮されます。プリフェッチからの要約キャッシュを使用して、冗長なクエリを回避します。

両方のパスは`runPasses`ヘルパー内で実行され、コンテキストアイテムを一度フェッチし、ミューテーションが発生したときにパス間でのみ再フェッチします。

**要約エスカレーション**（`internal/memory/summarize.go`）：

`LLMSummarizer`は3段階のエスカレーション戦略を実装します：

1. **通常モード** -- 主要な決定、根拠、制約、アクティブなタスクを保持します。ターゲット：input_tokens/3。
2. **アグレッシブモード** -- 永続的な事実と現在のタスク状態のみを保持します。通常モードがターゲットの150%を超えたときにトリガーされます。
3. **決定論的フォールバック** -- 文/行の境界でターゲットに切り詰めます。アグレッシブモードが依然として150%を超えるときにトリガーされます。

リーフ要約はソーストークンの1/3をターゲットとします。凝縮要約は1/2をターゲットとします（詳細を保持するためあまりアグレッシブではない）。

### コンテキストアセンブリ

`Assembler`は各LLM呼び出しのコンテキストウィンドウを構築します（`internal/memory/assembler.go`）：

1. コンテキストアイテムを**フレッシュテール**（最後のNメッセージアイテム、デフォルト20）と**古い**アイテムに分離。
2. フレッシュテールアイテムを`ai.Message`に解決 -- これらは予算に関係なく常に含まれます。
3. 残りの予算を古いアイテムで埋め、最新のものから。各アイテムが解決され、そのトークンが推定されます。予算を超えるアイテムは除外されます。
4. 古いイベント（時系列順）+ テールイベントを返します。

**要約XMLフォーマット**（合成ユーザーメッセージとして注入）：

```xml
<summary id="sum_abc123" kind="leaf" depth="0" earliest_at="..." latest_at="...">
  <parents>
    <summary_ref id="sum_parent1" />
  </parents>
  <content>
    Summary text here...
  </content>
</summary>
```

**トークン推定：** `(len(text) + 3) / 4`（JSON オーバーヘッドを含む英語テキストで約4文字/トークン）。

### メモリツール

`internal/memory/tool/`の統合`memory`ツールは、`action`パラメータを介してすべてのメモリ操作を提供します：

| アクション           | 目的                                                                                                                                                             | 主要パラメータ                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `grep`               | 部分文字列パターンでメッセージと要約を検索                                                                                                                       | `pattern`（必須）、`scope`（`messages`/`summaries`/`both`）、`limit`（デフォルト20） |
| `describe`           | 要約のメタデータ、内容、系統（親/子）を検査                                                                                                                      | `summary_id`                                                                         |
| `expand`             | 要約にドリル：ソースメッセージ（リーフ）または子要約（凝縮）を返す                                                                                               | `summary_id`、`token_cap`（デフォルト4000）                                          |
| `user_memory_update` | `ctx_agent_memory`のユーザーごと・エージェントごとの永続ノートの書き込み専用更新。内容は常にシステムプロンプトに注入されます。このアクションは書き込みのみです。 | `content`（必須）                                                                    |

ツールはコンテキストからセッションID、ユーザーID、エージェントIDを抽出します（`Pool.Chat()`によって設定）。

### 並行性

- **セッションごとのミューテックス** -- `Ingest`、`IngestBatch`、`Compact`は`withSessionLock()`経由でセッションごとのロックを取得し、同じ会話での同時ミューテーションを防ぎます。
- **グローバルミューテックス** -- セッションミューテックスマップと会話IDキャッシュを保護します。
- **会話IDキャッシュ** -- `getOrCreateConversation`は`sessionID → convID`マッピングをキャッシュします。作成後は不変であるため。

### 設定デフォルト

| 定数                      | 値   | 説明                                   |
| ------------------------- | ---- | -------------------------------------- |
| `DefaultFreshTail`        | 20   | コンパクションから保護されるメッセージ |
| `DefaultContextThreshold` | 0.75 | コンパクションをトリガーする予算の割合 |
| `DefaultLeafChunkSize`    | 10   | リーフ要約ごとの最小メッセージ数       |

### 統合

メモリエンジンはエージェントPoolに結び付けられています。セッションがそれを使用する場合：

1. 各メッセージは毎ターン後にデータベースに取り込まれます。
2. コンテキストは各LLM呼び出し前にデータベースから組み立てられます。
3. コンパクションはコンテキスト閾値に基づいて自動的に実行されます。

## アイデンティティとユーザーメモリ

エージェントアイデンティティとユーザーごとのメモリはデータベースに保存され、オプションでワークスペースファイルによってオーバーライドされます。

### 3層システムプロンプト

LLMに送信されるシステムプロンプトは3つの層から組み立てられ、それぞれオーバーライド可能です：

| 層                     | デフォルトソース                | ファイルオーバーライド                  | 説明                                                                                         |
| ---------------------- | ------------------------------- | --------------------------------------- | -------------------------------------------------------------------------------------------- |
| **基本**               | ビルトインシステム指示          | エージェントワークスペースの`SYSTEM.md` | LLMのコア動作指示。                                                                          |
| **エージェントソウル** | `settings_agents.system_prompt` | エージェントワークスペースの`SOUL.md`   | エージェントのアイデンティティ、個性、トーン。                                               |
| **ユーザーメモリ**     | `ctx_agent_memory.content`      | （なし -- 常にDBから）                  | ユーザーごと・エージェントごとのノート。自動的に注入されます。ファイルでオーバーライド不可。 |

層は順番に連結されて（基本、次にエージェントソウル、次にユーザーメモリ）最終的なシステムプロンプトを形成します。

### エージェントソウル

エージェントソウルは個性とトーンを定義します。`settings_agents.system_prompt`に保存され、管理パネルを通じて管理できます。エージェントワークスペース（`$ANNA_HOME/workspaces/{agent_id}/SOUL.md`）に`SOUL.md`ファイルが存在する場合、その内容がデータベース値よりも優先されます。

### ユーザーメモリ

ユーザーメモリは`ctx_agent_memory`テーブルに保存され、`(user_id, agent_id)`でキー指定されます。これにより、各ユーザーはエージェントごとに異なるノートを持つことができます。内容はセッション開始時に常にシステムプロンプトに注入されます。

エージェントは`memory`ツールの`user_memory_update`アクションを介してユーザーメモリを更新します。このアクションは**書き込み専用**です -- 現在のユーザー/エージェントペアの`ctx_agent_memory`行の内容全体を置き換えます。エージェントはツールを通じてユーザーメモリを読み取ることはできません。常にシステムプロンプト注入を通じて提供されます。

### エージェントワークスペース

各エージェントは`$ANNA_HOME/workspaces/{agent_id}/`に独自のワークスペースディレクトリを持ちます。このディレクトリには、ファイルオーバーライド（`SYSTEM.md`、`SOUL.md`）、スキル、その他のエージェントごとのデータが保持されます。
