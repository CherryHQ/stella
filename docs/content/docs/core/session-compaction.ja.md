---
title: セッションコンパクション
---

## ステータス

実装済み -- `internal/agent/pool_compaction.go`（オーケストレーション）、`memory.Engine`（SQLite永続化）、チャネルが`/compact`を公開。

## 問題

LLMランナーには有限のコンテキストウィンドウがあります。セッションがメッセージを蓄積すると、履歴は無制限に成長します。最終的にランナーのコンテキストがいっぱいになり、応答の劣化またはハード障害につながります。長期間のセッション（Telegramチャット、複数日のコーディングセッション）はこの壁にすぐにぶつかります。

重要なコンテキストを失うことなく古い履歴を圧縮し、ユーザーが手動で新しいセッションを開始する必要がない方法が必要です。

## 設計：ハンドオフスタイルコンパクション

コアアイデアは、コーディングエージェントで使用される「ハンドオフ」パターンから借用されています：コンテキストが大きくなりすぎたら、LLM自体に自己完結型の要約を作成するよう依頼し、古い履歴をその要約と最近のメッセージの小さなテールに置き換えます。

```
コンパクション前：
┌──────────────────────────────────┐
│ session header                   │
│ message 1                        │
│ message 2                        │
│ ...                              │
│ message N-20                     │
│ message N-19                     │  ← そのまま保持
│ ...                              │
│ message N                        │
└──────────────────────────────────┘

コンパクション後：
┌──────────────────────────────────┐
│ session header                   │
│ compaction { summary }           │  ← LLM生成の要約
│ message N-19                     │  ← 最後の20メッセージを保持
│ ...                              │
│ message N                        │
└──────────────────────────────────┘
```

要約は、ランナーが元のメッセージなしで会話を続行できるように構造化されています -- 目標、進捗、決定、変更されたファイル、現在の状態、ブロッカー、次のステップが含まれます。

## アーキテクチャ

```
Channel (/compact or auto)
    |
    v
Pool.CompactSession(ctx, sessionID)
    |
    ├─ getOrCreateRunner()       必要に応じてSQLiteからセッションをロード、ランナーを確保
    │
    ├─ collectFullResponse()     コンパクションプロンプトをランナーに送信、要約を収集
    │
    ├─ memory.Engine compaction  SQLiteに要約 + テールを保存
    │
    └─ kill runner               次のChat()はクリーンなコンテキストで新たに開始
```

### トークン推定

トークン推定は、保存されたメッセージのバイト長を合計し、4で割ります（大まかなヒューリスティック：JSONオーバーヘッドを含む英語テキストで約4バイト/トークン）。

### コンパクションプロンプト

プロンプトはランナーに構造化された要約を作成するよう依頼します：

- **Goal** -- 元のセッション目標
- **Progress** -- 完了または部分的に完了したもの
- **Key Decisions** -- 決定と根拠
- **Files Changed** -- コンテキスト付きパス
- **Current State** -- 何が機能し、何が機能しないか
- **Blockers / Gotchas** -- 問題やエッジケース
- **Next Steps** -- 具体的で実行可能なタスク

ガイドラインは自己完結性を強制します：要約は、以前の会話にアクセスできない読者にとって意味をなす必要があります。

### ストレージフォーマット

コンパクション要約は、`memory.Engine`を介してSQLiteデータベースにメッセージとして保存されます。`Load()`時、エンジンはコンパクションエントリを`ai.Message`のペア -- 要約を含むユーザーメッセージとアシスタントの承認 -- に変換するため、ランナーはそれを通常の会話履歴として認識します。

## トリガー

### 手動 -- `/compact`コマンド

CLIとTelegramの両方で利用可能：

```
/compact
```

`Pool.CompactSession()`を直接呼び出します。要約テキストをユーザーに返します。

### 自動 -- トークン閾値

`Pool.Chat()`は各メッセージの前に`Pool.NeedsCompaction()`をチェックします。推定トークン数が閾値を超えた場合、ユーザーのメッセージが送信される前にコンパクションが自動的に実行されます。

自動コンパクションが失敗した場合、システムは警告をログに記録し、完全な履歴で続行します -- ユーザーのメッセージをブロックすることはありません。

## 設定

コンパクション設定は、データベース設定テーブルの`compaction`キー下にJSONとして保存されます。管理パネルまたは設定API経由で設定できます。

フィールド：

- `max_tokens`: 自動コンパクト閾値（デフォルト：80,000、無効にするには`-1`に設定）
- `keep_tail`: そのまま保持する最近のメッセージ（デフォルト：20）

両方のフィールドは`CompactionConfig.WithDefaults()`を介してデフォルトが適用されます。

`max_tokens`を`-1`に設定すると自動コンパクションが無効になります。`/compact`は手動で機能します。

## ステートフルランナー

一部のランナー（Piサブプロセスなど）は独自のコンテキストをインプロセスで維持し、`Chat()`に渡される`history`パラメータを無視します。これらのランナーの場合、コンパクション後にプロセスを終了すると、利益なしにライブコンテキストが破壊されます -- 新しいプロセスはコンパクトされた履歴を再生できません。

ランナーは、オプションの`runner.Stateful`インターフェースを実装することでこれをシグナルします：

```go
type Stateful interface {
    Stateful() bool
}
```

ランナーがステートフルの場合、`CompactSession()`はランナーの終了をスキップします。コンパクトされた履歴は依然としてディスクに書き込まれます（クラッシュリカバリとセッション復元のため）が、ライブランナーはそのインプロセスコンテキストをそのまま維持します。

履歴からコンテキストを再構築するステートレスランナーの場合、ランナーは以前と同様に終了されるため、次の`Chat()`呼び出しはコンパクトされた履歴で新たに開始されます。

## セッションロード

`CompactSession()`は`getOrCreateRunner()`を使用します -- `Chat()`と同じパス -- そのため、セッションがディスクにのみ存在する場合でも機能します（例：プロセス再起動後、またはこのプロセスのライフタイムでアクセスされていないTelegramセッションの場合）。これにより、`/compact`は永続化されたセッションに対して常に利用可能です。

## 障害モード

| シナリオ                 | 動作                                     |
| ------------------------ | ---------------------------------------- |
| ランナーの要約失敗       | エラーを返し、セッションは変更されない   |
| データベース書き込み失敗 | エラーを返し、元のデータは保持される     |
| 自動コンパクション失敗   | 警告をログに記録し、完全な履歴で続行     |
| ランナーからの空の要約   | エラーを返す：「empty summary response」 |

すべての書き込みは原子性のためにSQLiteトランザクションを経由します。
